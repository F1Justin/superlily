# Superlily stable foundation architecture

本文记录 P1–P2 stable foundation 的架构边界。后续 P3–P5 与 history archive 在其
独立合同和 ADR 中扩展该基础；本文不承担当前路线排序。Phase one remains the
observability spine. Phase two adds deterministic canonical decisions and an
optional, fail-open claim path without moving tool execution into Core.

```text
Lily / NoneBot  ── bounded telemetry queue ─┐
                 ── optional claim request ─┼─> Lily Core ─> dedicated PostgreSQL
Nekro 2.2.1   ── bounded telemetry queue ───┤
                 ── optional claim request ─┘
```

Telemetry remains asynchronous and bounded. Claims are disabled by default;
when enabled, a timeout, error, stale registry, missing second observation, or
uncertain decision returns `abstain` and preserves existing behavior. Lily
suppresses only outgoing send APIs for an enforced deny, leaving recorders and
observer matchers running. Nekro uses `BLOCK_TRIGGER`, which preserves its
message history while skipping agent execution.

Both bridges publish a conservative typed platform-capability snapshot in
their heartbeat. The initial QQ profile claims only text, image, reply, and
mention. Missing or unlisted capabilities remain unsupported/unknown. Phase 3
tool results and Phase 4 renderers can therefore negotiate outputs without
embedding QQ assumptions in the tool itself.

## Event identity

- A bridge-reported `source_event_id` identifies one account's platform event.
  This value is retained on the observation as `reported_source_event_id` and
  is never treated as the canonical identity by itself. QQ message bridges use
  versioned, content-free `qq:source:v2:<sha256>` IDs over canonical
  conversation and allowlisted native identity rather than NapCat's
  collision-prone short `message_id`. Core returns HTTP 409 if a reported ID or
  idempotency key is reused with conflicting identity.
- Core assigns the canonical `source_event_id`. Correlation v3 applies only to
  QQ group-message events with a sender and NapCat `real_seq`; private chats
  remain uncorrelated until they have independent identity evidence. Its key is platform,
  canonical conversation, sender, event kind, and `real_seq`; text and
  account-local message IDs are excluded. Native platform time is a conflict
  guard and permits matching fingerprints to merge despite adapter-normalized
  timestamp skew; the bounded event-time window remains only for payloads
  without native time. Missing or conflicting identity creates a separate
  source event and a visible correlation diagnostic.
- Canonical QQ message events use event type `message`; adapter-specific values
  such as `message.group.normal` remain observation-side details.
- `observation_id` is generated by Core for one bot instance's view of that
  source event.
- Phase 2a.1 records a content-free `metadata.native_identity` allowlist from
  the original OneBot event. The important candidate is NapCat `real_seq`;
  account-local `message_id`, type, time, conversation, and sender fields are
  retained as comparison evidence. Phase 2a.1 collected this evidence without
  changing correlation; Phase 2a.2 now uses the validated group-message key.
  Nekro temporarily joins its raw OneBot event to its normalized `ChatMessage`
  through a bounded in-memory TTL cache because Nekro otherwise discards
  `real_seq` during conversion. Phase 2a.2 promotes the verified `real_seq`
  combination to correlation v3.
- Phase 2a adds `event_links` for message references. A link starts at one
  observation/source event and may resolve to a canonical target source event.
  If the bridge only knows an account-local target message ID and Core cannot
  resolve it yet, the link stays `unresolved` for later import/backfill.
- Phase 2b adds one recomputable `event_decision` per canonical event. Every
  new observation, resolved reply link, or relevant response can increment its
  revision. Command text prefers Lily's view; reply routing uses the sender of
  the referenced message and ignores QQ's decorative automatic `at`. Messages
  authored by a known bot instance remain first-class graph nodes but policy
  v2 classifies them as `observe_only / bot_message_observed`, so a bot reply
  containing a command or “莉莉” cannot create a false second trigger. Policy
  v5 additionally preserves NoneBot's leading-segment command eligibility,
  recipient-bound private routing, and conservative unresolved/ambiguous reply
  behavior.
- Phase 2b.1 moves command detection into a TOML command registry. The
  registry records deterministic Lily/NoneBot triggers, source plugins,
  permissions, and sensitive control commands so shadow decisions can be
  audited before any future claim-lock enforcement. Phase 2b.2 adds
  authenticated, hash-verified runtime snapshots from the loaded NoneBot
  plugin tree. Unknown runtime triggers remain visible and force claim
  abstention; they are never promoted automatically into trusted rules. A
  matcher with additional custom rules or permissions is explicitly marked
  incomplete because a trigger-only approximation cannot prove that it will
  run for the current sender.
- The decision/outcome audit joins canonical decisions to actual response
  records. Lily provides native `event_context`. Nekro's public response hook
  has no native trigger identifier, so the bridge mirrors the per-chat
  scheduler and binds `task_context` to the current task while retaining a
  separate pending next-task source. Multiple sends from one task keep the same
  attribution; a later message cannot overwrite it. Send timeouts are recorded
  as ambiguous completion rather than confirmed non-delivery.
- Phase 2c records per-instance `event_claims`. Only actionable `command` and
  `talk` decisions can produce an allow. Ownership enforcement requires
  correlation v3, two observations, sufficient confidence, a fresh runtime
  registry, no unregistered runtime match, deterministic reply routing, and
  an online target. Command enforcement additionally requires a fully
  introspected, public, non-sensitive matcher. Policy v6 adds one no-owner
  exception: deterministic `reply_to_other_observed` without an explicit Lily
  summon may deny each requesting instance after the identity/confidence gates,
  but can never allow one. It needs no multi-observer ownership quorum, so the
  same rule works in a Lily-only command group.
- An enforced `allow` additionally requires every other instance that observed
  the canonical source to have acknowledged an already committed enforced
  `deny` after installing local suppression. This closes the response-loss
  hole where Core committed a deny but the bridge timed out and failed open
  before receiving it. A deny may stand alone safely; a missing peer
  acknowledgement turns allow into
  `abstain / claim_peer_suppressions_not_acknowledged`.
- Every recomputation of one canonical decision uses the same source-specific
  transaction lock, whether it was triggered by an observation, a late
  response, reference resolution, or claim backfill. Correlation locks alone
  are insufficient because response ingestion follows a separate path.
- `Idempotency-Key` is scoped to the authenticated instance. Replaying a
  delivery returns the existing observation or response.
- Responses may have no trigger. Scheduled sends, random replies, and proactive
  messages are valid first-class records.

Redis is intentionally absent at current scale. PostgreSQL transactions and
advisory locks serialize correlation and claim ownership. Redis remains an
option for later distributed rate limits, leases, and work queues; it is not a
prerequisite for the bounded QQ canary.

PostgreSQL advisory locks use a 64-bit key derived from the full correlation
fingerprint. A 64-bit lock-key collision can transiently serialize unrelated
events, but it cannot merge source events because the database stores and
compares the full fingerprint. The relevant risk is concurrent lock contention,
not cumulative lifetime message count.

Phase 3 does not extend this bridge identity into provider authority. Tool
providers receive separate authenticated identities; Git-reviewed descriptors,
immutable database copies, provider inventory, heartbeat, eligibility and
execution mode remain separate layers. See `PHASE3_TOOL_REGISTRY.md`,
`PHASE3_ACCEPTANCE.md`, and the desired/reported/effective/actual operator view
in `CONTROL_PLANE.md`.

## C0-D collection reliability insertion

C0-D is inserted after deployed Phase 3a and before Phase 3b without reopening
the Phase 2 routing acceptance. It adds capture-policy/completeness snapshots,
normalized basic platform actions, bridge-spool commit receipts and collector
watermarks. It adds no model, tool, claim or delivery authority.

The durable spool remains adapter-local so Core never receives QQ credentials.
The adapter writes first, submits an authenticated `spool_id + sequence +
record_sha256`, and deletes only after a matching Core receipt. Core keeps the
account-local namespace and exposes highest-seen versus highest-contiguous
watermarks. Platform-reported occurrence time, bridge capture time, Core receive
time and database commit time remain separate so a reconnect backlog cannot be
mistaken for genuinely simultaneous messages. C0-D2/D3 provide the actual
spool files, quotas, quarantine and coverage operations.

C0-A is deliberately separate. Nested merged-forward expansion, formal
`archive_full` rollout, portable exports, reconstruction, retention/deletion
propagation and old-history import do not block Phase 3b once C0-D is stable.
