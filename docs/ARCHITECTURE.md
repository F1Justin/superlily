# Phase-one architecture

Phase one is an observability spine, not a message-control plane.

```text
Lily / NoneBot  ── bounded background queue ─┐
                                             ├─> Lily Core ─> dedicated PostgreSQL
Nekro 2.2.1   ── bounded background queue ──┘
```

Core has no path back to either bot. Both bridges are fail-open and use short
HTTP timeouts. Losing Core can lose telemetry, but cannot stop a matcher,
change a response, or trigger a retry storm.

## Event identity

- A bridge-reported `source_event_id` identifies one account's platform event.
  QQ/OneBot message IDs are account-local in the current deployment, so this
  value is retained on the observation as `reported_source_event_id` and is
  never treated as a cross-account identity.
- Core assigns the canonical `source_event_id`. For eligible QQ text messages,
  observations correlate only when platform, normalized conversation, sender,
  normalized text, and a two-second time window agree. The first phase of
  correlation deliberately excludes non-text events.
- Canonical QQ message events use event type `message`; adapter-specific values
  such as `message.group.normal` remain observation-side details. Account-local
  message IDs are stored only on observations.
- `observation_id` is generated by Core for one bot instance's view of that
  source event.
- Phase 2a adds `event_links` for message references. A link starts at one
  observation/source event and may resolve to a canonical target source event.
  If the bridge only knows an account-local target message ID and Core cannot
  resolve it yet, the link stays `unresolved` for later import/backfill.
- Phase 2b adds `event_decisions` in shadow mode. Core records a rules-based
  decision for each canonical event, such as `observe_only`, `command`, `talk`,
  or `ignore`. These decisions are audit signals only; bridges do not consult
  them before running existing matchers.
- Phase 2b.1 moves command detection into a TOML command registry. The
  registry records deterministic Lily/NoneBot triggers, source plugins,
  permissions, and sensitive control commands so shadow decisions can be
  audited before any future claim-lock enforcement.
- `Idempotency-Key` is scoped to the authenticated instance. Replaying a
  delivery returns the existing observation or response.
- Responses may have no trigger. Scheduled sends, random replies, and proactive
  messages are valid first-class records.

Redis is intentionally absent. Claim locks, distributed rate limits, and work
queues still belong to the later enforcement part of phase two. Phase 2a records
and resolves references; Phase 2b records shadow decisions and reads the command
registry. Neither phase takes over message sending.
