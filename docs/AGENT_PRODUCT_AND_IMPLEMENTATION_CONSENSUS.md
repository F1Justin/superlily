## 2. 产品定位：群聊 Agent 不是代码 Agent 的缩小版

Superlily 面向群聊、私聊和未来社群入口。它与 Claude Code、pi 等代码 Agent 共享
“模型可以观察、调用工具、根据结果回修并交付结果”的基本结构，但运行环境不同：

- 代码任务通常有相对明确的 goal、独占工作区和可运行的测试；
- 群聊消息经常只有一句话，没有完整 goal，参与者还会随时插话或改变话题；
- 群聊是公共空间，首条响应延迟、消息噪声、成本和错误扩散都更敏感；
- 很多问题没有机器可验证的唯一终态，只能依赖来源、计算、交叉检查和不确定性表达；
- 一条失败的代码尝试通常只影响任务工作区，一条自信但错误的群聊回答会直接影响多人。

所以 Superlily 不能把每条消息都升级成长任务，也不能照搬“持续工作直到测试通过”的
交互节奏。它需要一个默认很轻、必要时才逐步升级的群聊 Agent。

从用户视角，莉莉应保持一个连续的角色和表达身份。内部可以有 Command、Talk、
Reserve 等逻辑角色，也可以有多个 QQ 账号、模型 Provider、工具 Provider 和渲染器；
这些实现边界不能要求用户理解，更不能因为昵称、头像或展示身份一致就取消内部的
principal、role、lease、fence 和审计边界。

## 3. 绝大多数消息走快速路径

约 99% 的用户需求只是一个小问题，期待直接、快速的回复。默认行为应当是：

1. 使用当前消息、明确引用、短会话窗口和最小身份/能力摘要；
2. 使用经济、低延迟模型；
3. 能直接回答就直接回答，不调用工具、不检索历史、不发送进度消息；
4. 短答案优先发送原生文字，不为“显得高级”强制渲染成图片；
5. 不把普通闲聊创建成多轮研究任务，也不要求用户先补全形式化 goal。

只有在任务确实需要事实更新、精确计算、读图、代码执行、历史检索、多个相互依赖步骤，
或模型对答案没有足够把握时，才进入较重的 AgentRun。

快速路径不是“永远用最弱模型”。它是默认预算和延迟策略；明确高难、强时效或高风险
问题可以在第一轮就升级，不能为了省一次模型费用先公开发送一个大概率错误的答案。

## 4. 模型负责判断与选择，Harness 负责边界

系统不应人工编排所有可能的固定流程。例如，用户拍一道题问莉莉怎么做时，不应写死：

```text
读图 -> 判断数值计算 -> Wolfram -> Python -> TeX -> 夜间黑底图 -> QQ
```

更合理的执行方式是：

1. 模型理解当前问题和可用证据；
2. 模型判断能否直接回答，是否需要读图、搜索、计算、写代码或调用领域工具；
3. Harness 只向模型披露当前有资格使用的资源；
4. 模型提出结构化调用，Core 校验身份、权限、schema、预算和 Provider 状态；
5. 工具结果作为有来源、有界且不可信的数据返回模型；
6. 模型可以在总预算内修正参数、换工具或追加一次验证；
7. 模型生成最终内容及表达意图，Renderer 和 adapter 完成确定性排版与平台交付。

模型应当决定：

- 问题真正需要什么信息和工具；
- 是否值得继续一轮；
- 中间结果是否相互矛盾；
- 最终答案强调什么；
- 更适合文字、公式、代码、表格还是图表。

系统必须固定：

- 哪些工具和资源可以被发现；
- principal、会话范围、权限、确认和副作用边界；
- 最大模型轮数、工具调用数、并发、时间、token、费用和产物大小；
- lease、fence、取消、超时、重试和不明确完成的处理；
- 结构化结果、artifact、渲染和发送怎样留账；
- 平台能力不足时允许哪些显式降级。

这不是用人工流程压制模型能力，而是把可从更强模型中获益的判断留给模型，把权限、
成本、幂等和安全等不能依赖模型自觉的部分交给 Harness。所谓 `the bitter lesson`
不意味着把数据库凭据、平台 token、无限工具和全部历史一次性交给模型。

## 5. 渐进式披露

### 5.1 初始上下文

一次普通群聊请求的初始上下文应当小而稳定，只包含：

- system、安全和角色策略的版本化摘要；
- 当前规范化消息、明确引用及可得图片；
- 有界的最近会话窗口；
- 当前 sender、conversation、principal 和平台能力摘要；
- 少量当前真正 eligible 的工具短描述；
- 本次 AgentRun 的剩余预算。

不得默认注入全量群历史、全部用户档案、整份文档库、所有插件说明、完整工具 schema、
数据库导出或大段运行日志。

### 5.2 工具目录分层

工具披露至少分三层：

1. 类别或能力摘要，例如“精确数学计算”“公式渲染”“受限历史检索”；
2. 少量候选工具的短描述、风险级别和顶层参数；
3. 模型明确选择候选后，才读取完整 descriptor、schema 和必要用法。

不 eligible 的工具不应只标成“禁止”后仍全部塞进 prompt；默认应不可见。需要确认、
费用较高或数据范围敏感的工具可以显示受限摘要，但不能因此获得执行权。

### 5.3 资源也按需发现

文档、历史、状态、文件和资源目录应当由工具按需提供索引或有界导出。默认上下文没给，
不代表模型永远无法发现；正确做法是提供一条低成本的发现路径，而不是预先塞满上下文。

检索结果必须带来源、范围、时间和截断状态。没有结果、权限不足、索引过旧和真实不存在
是不同状态，不能都伪装成“没有相关信息”。

## 6. Typed tool 与 Unix 原语并存

模型已经非常熟悉 `rg`、`grep`、`find`、`jq`、`sort`、`sed` 和管道组合。在受限的
只读或临时沙箱中，这些原语通常比为每一种查询方式制造一个狭窄 API 更有泛化能力。
系统应尽量把经过授权的文档、导出数据、代码和资源以普通文件形式提供，让模型自主
组合成熟工具。

但以下能力仍必须使用 typed tool 和 Core authority：

- 跨用户、跨群或按隐私策略查询数据库；
- QQ reaction、群管、撤回、转发和其他平台操作；
- 配置修改、服务控制、持久状态写入和付费调用；
- 需要 principal、确认、幂等、审计或不明确完成处理的操作；
- 不能安全复制进沙箱的实时状态或敏感资源。

`history.search` 的意义不是重新实现一个比 `rg` 更笨的文本搜索器，而是创建一份经过
身份授权、限定 conversation scope、可审计、可截断且有保留策略的历史视图。模型拿到
安全导出或沙箱副本后，仍可继续使用 Unix 原语做二次筛选和组合。

同理，不应为每个 Linux 命令包装一个独立 Tool Registry descriptor。应注册的是一项
有明确资源边界的沙箱执行能力；具体使用哪些只读命令和管道，由模型在沙箱策略内决定。

## 7. 自然语言复用确定性命令

用户说“帮我换个老婆”，预期可以等价于该用户主动执行现有“换老婆”命令。正确实现
不是让模型生成一段伪造聊天文本再注入 NoneBot matcher，而是：

```text
自然语言
  -> 模型提出同一结构化工具和参数
  -> Core 使用真实 sender principal 重新做权限与确认
  -> 与命令入口共享执行 Provider、结果结构和审计
  -> Renderer/adapter 交付结果
```

命令入口继续保留，作为低延迟、确定性、可回滚的兼容路径。自然语言和命令可以共享工具
语义，但不能共享未经验证的 caller identity。即使原命令没有危险，只要它会修改持久
状态，也必须先完成 Phase 5c 所需的 principal、授权和确认边界。

实现顺序应当是：

1. 先让自然语言 shadow 识别对应工具，但不执行；
2. 对只读、公开命令逐一开放 Agent caller；
3. 对计算型工具增加总成本和循环预算；
4. 最后才迁移低风险写命令；
5. 群管、配置、服务和跨平台写操作继续使用更强确认。

不得为了自然语言便利，维护第二份与现有命令逐渐漂移的业务实现。

## 8. 群聊长任务与进度消息

群聊任务通常不需要进度同步。只有预计明显超过普通回复时延、需要多轮昂贵调用，或用户
明确要求持续跟进时，才发送一条克制的进度消息，例如“我在核对公式和数值结果”。

进度消息应满足：

- 不泄露 chain-of-thought、内部 prompt、token、路径、凭据或原始异常；
- 说明正在进行的外部可理解阶段，而不是表演式地逐工具播报；
- 同一任务有更新节流，避免每次模型轮次都刷群；
- 新用户消息可以修正或取消仍在运行的任务；
- 最终失败时给出有用的安全摘要，不假装已经完成；
- 进度发送本身也有 delivery intent、幂等和回执。

AgentRun 应允许“没有完整 goal”的请求：模型可以根据当前话语形成一个有界的暂定任务，
直接完成低风险部分。只有缺失信息会显著改变结果、权限或成本时，才向用户追问。

## 9. 输出内容、渲染与发送分离

Phase 4 已经建立以下边界：

```text
模型或工具生成结构化内容
  -> RenderDocument
  -> 确定性 Renderer / artifact
  -> capability-aware DeliveryPlan
  -> 平台 adapter
```

模型不应为普通数学回答临时编写 Matplotlib/Pillow 排版程序，也不应决定每个字符的
像素位置。Matplotlib 适合真实曲线、统计图和几何图，不是中文数学文档排版器。
Renderer 负责字体、换行、公式基线、主题、尺寸、分页、安全解析和确定性降级。

默认表达策略是：

- 几行可以说清的问题直接发原生文字；
- 单个公式可以使用公式 artifact；
- 较长且混合中文、数学、代码或表格的内容使用统一文档渲染；
- 真正需要观察数值关系时才生成图表；
- 平台不支持目标格式时，按记录在案的 fallback 降级；
- 主题、深浅色、字体和 locale 是渲染 profile，不得改变计算和语义结果。

“模型决定最终表达方式”指模型可以给出内容结构和偏好，不等于模型可以绕过
RenderDocument、直接写 HTML、访问本地文件或持有平台发送能力。

## 10. 成本可持续的模型路由

不需要给所有群、所有消息常驻高端模型。模型路由必须同时考虑正确率、时延、数据策略和
长期费用。

默认路由使用经济模型。以下信号可以在预算内触发更强模型、搜索或确定性工具：

- 用户明确要求严谨证明、深入研究或多步分析；
- 当前问题属于高难学术、复杂代码、复杂图片或长上下文综合；
- 问题具有强时效性，模型静态知识不足；
- 医疗、安全、财务等错误代价较高；
- 首个模型给出低置信度、内部矛盾、schema 失败或无法验证的答案；
- 特定群配置了更敏感的学术升级阈值；
- 用户在当前对话中明确指出错误并要求重答。

对于经常讨论学术问题的群，不应采用“先让便宜模型公开乱答，被骂后再升级”的固定策略。(此条我——f1justin，持保留意见)
可以在发送前用领域、问题长度、数学符号、引用需求和模型不确定性进行预路由；成本仍由
群、每日、会话和单次 AgentRun 上限控制。

路由决策必须记录所选 profile、原因、价格快照、fallback 和数据分类。模型 Provider
不可仅因在线就获得某类聊天数据；fallback 必须满足同一数据处理策略。高端模型故障时，
系统可以明确降级、只给可验证部分或暂缓回答，不能无提示换成不满足要求的模型。

## 11. 时效信息与“不要梦到什么说什么”(此条我——f1justin，持保留意见)

模型的静态知识不能当作搜索结果。对新闻、版本、价格、人物职务、活动状态、服务器实时
情况等可能变化的信息，Agent 应当：

1. 识别知识时效风险；
2. 在有权限和预算时调用搜索或权威状态工具；
3. 保留来源时间、检索时间和范围；
4. 搜索失败时明确说明无法实时核实；
5. 不用流畅措辞填补证据缺口。

是否需要实时检索由模型判断，但 Harness 可以为明显的时效类别设置最低证据策略。
搜索工具与普通网页内容同样是不可信输入，不能因为“联网了”就跳过来源质量、注入和
数据边界。

## 12. Reaction 与纠错是弱反馈，不是自动训练标签

用户给莉莉的回复贴拳头、赞、疑问等 reaction，或引用回复指出错误，确实是重要的产品
反馈来源。但任何单个 reaction 都可能是玩笑、社交互动、对内容之外因素的回应，平台
emoji ID 也不天然等于固定情绪。

未来使用这些事实时应当：

- 把 reaction、撤回、用户纠正、重问、人工评分和最终是否接受分开；
- 结合目标消息、操作者、时间、后续对话和群语境评估；
- 先用于离线质量分析、路由阈值和样本发现；
- 不把一个拳头自动变成负奖励，也不自动微调模型；
- 不因为负反馈就在公共群自动刷一条昂贵重答；需要当前用户请求或明确策略；
- 保留可解释的版本、范围和退出机制。

平台事件如何采集已经由 C0-D 处理，本文只规定后续产品语义。采到事实不等于已经取得
训练、画像、跨群归因或自动行为授权。

## 13. 为未来未知入口保留通用能力

未来可能接入社群活动系统、OBS、Fumo、皮套、传感器或现在无法想象的实体。Core 不应
为每一种设备预写一棵固定推理流程。新的 adapter 应声明：

- 它产生哪些事件和身份线索；
- 它能执行哪些 capability 和 intent；
- 它有哪些资源、速率、在线状态和安全限制；
- 它如何返回 acknowledgement、失败和不明确完成；
- 哪些内容可以进入 Agent 上下文和 artifact。

模型可以根据这些经过权限过滤的能力摘要做选择，但新入口不能绕过已有的 principal、
tool、artifact、delivery、confirmation、lease、fence 和 audit 边界。实体动作通常比
发一条群消息风险更高，应使用更窄的 allowlist、更强确认和物理安全停止机制。

## 14. Phase 5 以后建议实施顺序

### 14.1 Phase 5a：先观察模型会怎么选

- 完成模型 profile、真实 Provider 和默认禁用部署；
- 在不执行、不发送的前提下运行 planner-only shadow；
- 用真实但经范围控制的群聊样本评估 direct answer、tool proposal 和 abstain；
- 重点测量不必要调用、漏调用、错工具、参数错误、禁用工具请求、时效问题和成本；
- 不把未授权公开群合成探针当作默认验收方式；`708309706` 使用上文长期例外。

### 14.2 Phase 5b：逐个开放只读/计算工具

首个验收工具使用 `wolfram.run`，因为它能证明模型选择、结构化参数、真实计算、结果
回注和最终回答的完整闭环。`status.inspect` 是偶用插件能力，不承担 Agent 架构前置
门的角色；只有出现独立产品需求时才进入自己的 canary。`latex.render` 及后续搜索、
文档或沙箱资源能力也分别审阅，不为凑固定命令目录而开放。

每次只扩大一个 exact conversation、一个工具、一个 descriptor、一个 Provider 和有界
次数。工具结果回到模型后仍受总轮数、总时长、费用、重复循环和结果字节预算约束。

### 14.3 Phase 5c：再做自然语言写操作

- 先建立真实 principal、role 和 authorization；
- 确认必须绑定规范化参数、精确副作用、scope、expiry 和单次 nonce；
- 参数或 policy 变化后重新确认；
- 不明确完成进入人工检查，不因模型坚持而重试；
- 从低风险、用户本人范围内的状态修改开始，群管、配置和服务操作最后开放。

### 14.4 后续阶段

- Phase 6 负责健康、事件和角色 failover，不把 Reserve 变成第三个普通聊天 Agent；
- Phase 7 用真实第二平台证明 adapter 边界；
- Phase 8 才建立受 conversation scope 和保留策略约束的历史、文档和记忆检索；
- Phase 9 以后接活动、实体、avatar 和更复杂社群操作。

后续阶段可以复用本文原则，但不能为了尽快实现记忆、路由或实体能力而跨越当前阶段
authority。

## 15. 验收指标

Agent 能力不能只用“能调用工具了”验收。至少应持续观察：

- 普通问题的首条响应延迟和直接回答率；
- 不必要工具调用率、应该调用却漏掉的比例和错工具率；
- 参数 schema 有效率、重复循环和预算耗尽率；
- 工具结果与最终答案的引用、数值和单位一致性；
- 时效问题的检索率、来源质量和无证据断言率；
- 每群、每日、会话和任务的模型/工具成本；
- 取消、用户修正和新消息打断后的收敛；
- 原生文字、公式和长文渲染的可读性与降级原因；
- reaction、纠错和重问所指向的高风险样本；
- 命令路径延迟和可用性是否仍独立于模型健康；
- 是否出现任何未经确认的写操作或平台发送。

指标用于发现问题和调整受审阅策略，不自动扩大权限。离线评测、shadow、精确 canary、
稳定窗口和一键回滚仍是每个 authority 增量的基本发布纪律。

## 16. 明确不做的事

- 不为每类问题预写一条固定工具流水线；
- 不默认把所有历史、记忆、文档和工具 schema 塞进 prompt；
- 不让高端模型常驻所有群和所有消息；
- 不让模型直接持有数据库、Provider、artifact、平台或设备凭据；
- 不让 Tool Provider 或 Renderer 直接发送平台消息；
- 不让模型临时编写页面排版代码替代统一 Renderer；
- 不把 reaction 直接解释成正负训练标签；
- 不通过伪造聊天命令复用现有 matcher；
- 不为自然语言能力复制一套与命令实现并行漂移的业务逻辑；
- 不因为未来入口未知就取消当前的类型、权限、预算和审计边界；
- 不把“模型很强”当成取消 fail closed、确认、幂等和回滚的理由。

## 17. 新对话接手检查表

新的实现对话在开始工作前应依次确认：

1. 当前分支、Git 历史、工作区和生产阶段是否已变化；
2. `README.md`、`ROADMAP.md` 和当前 `PHASE*.md` 的已签署/未签署边界；
3. 本次需求属于快速回答、渲染、Agent planning、工具执行、模型路由、检索还是写操作；
4. 本次变更增加的是实现、caller、副作用、平台、数据范围还是 failover authority；
5. 是否可以先做合同、shadow 或精确 conversation canary；
6. 命令兼容、旧路径回滚和“除精确授权测试群外不主动发送”纪律是否保留；
7. 验收指标是否覆盖正确性、时延、费用、错误收敛和未授权行为；
8. 新设计是否与本文共识冲突；若产品共识发生变化，应先更新本文，再修改跨阶段路线。

这份检查表不要求每次重新设计整个系统。它的作用是让后续 AI 在会话切换后仍从同一套
产品原则出发，同时只实施当前被授权的最小切片。
